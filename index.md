[[wiki/codebase/files/auto_connect_system|auto_connect_system.py]] — **the most significant confirmed bug found this session**: the "auto-join all packaged agents on startup" feature cannot fire for anyone, ever, under the current code. `scan_agents_folder()` globs `DW_*`-prefixed directories; [[wiki/codebase/files/packager|packager.py]]'s actual current agent-directory naming is plain `{agent_id}`, no prefix — confirmed three independent ways (packager.py's own "no `DW_` prefix" comments at the real construction site, a matching comment in `main.py`, and the shared `Config.NPC_APPLICATIONS_DIR` root both files agree on). Its `GOD_ABILITY_NAMES` table is the exact file [[god-abilities]] already covers in real depth — cross-checked entry by entry against that page's existing table (all six gods, including the `summon_vexes`/`summon_fangs`/`retract_tentacles`/`emerge` additions) and confirmed to match exactly, no correction needed. One genuinely nice confirming find: this file's `god_to_controls()` carries its own independent copy of the same `DIM-03` ability-index-decoding fix already documented on [[god-abilities]] for `god_controls.py`'s `decode_action()` — the identical bug (treating a discrete integer output as a continuous range needing a mapping formula) existed in two separate files' parallel implementations, with matching fix comments in both, real evidence for how tightly these two files have to stay in lockstep rather than just an assertion of it.

[[wiki/codebase/files/agents_json_manager|agents_json_manager.py]] — 33 lines, a pure compatibility re-export of `mc_uuid.AgentNameManager` under an old name, nothing more. Confirms [[main]]'s already-documented `get_agents_manager` import resolves to this file's `get_manager()` exactly.

[[wiki/codebase/files/chat_backend|chat_backend.py]] — **resolves the thread flagged during [[main]]'s ingest**, and the answer is the opposite of what was speculated: not a third, possibly-current chat implementation, but the oldest and most disconnected one. A complete, standalone Flask + Flask-SocketIO server (the only non-FastAPI file in this whole ingest), confirmed orphaned by direct search — nothing anywhere imports it, its two push functions have zero callers. Its own `handle_user_message()` is an explicit stub (`# (Replace with planner/LLM later)`, hardcoded `"I heard: {text}"` replies, never touching `agent.brain`), despite the file's own header comment claiming `(finalized)`. Not dismissed as a forgotten scratch file, though: `flask`/`flask-socketio` are still listed in `requirements.txt` with purpose comments describing exactly this file's role, meaning this was a real, deliberate early direction for "the web interface" that got superseded by the FastAPI approach everything else uses, with the dependency lines simply never pruned. Also runs on port 8765 — the same port [[main]]'s dead `start_chat_interface` and [[chat_launcher]]'s live one both use for serving the built frontend — not a live collision since nothing calls this file automatically, but a real one if anyone ever ran it manually alongside the frontend server.

[[wiki/codebase/files/dw_controller|dw_controller.py]] — `ControllerRuntime`: real host-hardware access (OpenCV camera, `sounddevice` microphone), permission-gated, feeding directly into agent memory and emotion. Resolves both pointers carried forward as open threads: [[agent]]'s `_get_controller()` singleton and its four `/api/controller/*` routes, confirmed matching this file's constructor exactly, including a deliberate `__new__`-based special case for device detection without a full agent. Mostly confirmatory rather than a new discovery — one small, low-stakes note: `/api/controller/status`'s `hasattr()` guards check for attributes `ControllerRuntime.__init__` always sets unconditionally, the same minor defensive-against-a-guaranteed-interface pattern already documented at length for [[chat_system]], here harmless and small.

[[wiki/codebase/files/mc_uuid|mc_uuid.py]] — the most-referenced still-unread dependency across the whole session, confirmed to be exactly what every prior citation said it was: `AgentNameManager`, the single source of truth for `agents.json`. **New, still-open finding, added to [[known-issues]]**: this file's `get_minecraft_uuid()` and [[minecraft_launcher]]'s own `_offline_uuid()` both claim to compute Minecraft's offline-mode account UUID and don't agree — verified directly by comparing what each function actually hashes, not assumed from similar names. This file matches Java's well-documented `UUID.nameUUIDFromBytes()` exactly (no namespace prepending); `minecraft_launcher.py`'s `uuid.uuid3()` call does prepend a namespace UUID's bytes per RFC 4122, producing a different hash input and therefore a different UUID for the same username. Unlike the earlier `-l` flag question this session, both implementations are directly in this codebase and the external behavior they're each matching (or failing to match) is unambiguous, standard, documented JDK behavior — not a possibly-divergent external tool fork. Noted on [[minecraft_launcher]] directly.

[[wiki/codebase/files/validation|validation.py]] — six well-built Pydantic request-validation models (chat, file upload, agent spawn, controller activation, task switch, player event), closing out the Python-side ingest on a fitting note: **none of the six is used anywhere.** Confirmed by direct search across `main.py` and `agent.py`, the only two files defining routes these models are shaped for — zero references in either. The only mention anywhere outside this file is a PyInstaller hidden-import string in `config.py`, not a real usage. Every real route this ingest read validates its own input manually instead, ad hoc, per field, at the call site — a real, working, if less rigorous, alternative to the centralized validation layer sitting unused beside it.

**This closes the Python-side per-file ingest** — every file from `main.py` through `utils/validation.py` now has its own page. The Java mod layer and the Electron frontend remain topic-level only.

### Java mod layer — Python-dependent files first (2026-07-05, ongoing)

Per Devlord's direction, working the Java side (`DivineWorld` + `DWClientBot`, ~70 `.java` files total) in two phases: the subset that actually touches the Python backend first, full per-file sweep after. The priority subset was identified by search, not name-guessing — grepped both mod source trees for actual HTTP-client/socket/`ServerSocket` code and known-port references, rather than assuming from filenames which files matter.

[[LLMOracleBrain]], [[OllamaManager]], [[OracleSystem]] — the whole Oracle-package trio, resolving the `LLMOracleBrain` thread carried since `main.py`'s own ingest, and resolving it in the opposite direction from how it was left. [[oracle-two-systems]] already documented these three files in detail as "System B" — a self-contained, Java-only, Ollama-backed tutor NPC with zero connection to `NPCAgent`/`BrainCore`/the Python stack. **This means a correction, not just a confirmation**: [[main]] and [[chat_system]] had both floated `LLMOracleBrain` as a plausible, unconfirmed explanation for `chat_system.py`'s `hasattr()` defensiveness around god agents' brains. Read directly, that doesn't hold — every god agent, Oracle god-type included, uses the same `BrainCore` as every NPC, confirmed both by [[oracle-two-systems]]'s own System A section and by this file's own content having nothing to do with god agents at all. The `hasattr()` defensiveness is genuinely unexplained again; corrected on both pages and here. One real, concrete, positive finding alongside the correction: [[oracle-two-systems]]'s account of `/oracle teach` routing through `PythonBackendClient.notifyChatHeard()` into an agent's perception as an ordinary overheard-chat event, with no distinguishing flag anywhere in the payload, checked out exactly against the source, including a genuinely nice cross-language detail — the teaching-materials folder resolution explicitly mirrors [[mc_uuid]]'s `AgentNameManager._find_config_path()` fallback chain, by the Java file's own admission, not a coincidence. And a concrete, named consequence of the already-known `/api/agents/chat_heard` bug: `/oracle teach` calls exactly that broken endpoint, so every delivery attempt currently fails on the Python side — not just an abstract "no working path," a real feature broken by it.

[[NetworkHandler]], [[ServerGodAbilityExecutor]], [[GodDisguiseHandler]] — **fully resolves [[god-abilities]]'s open question, read directly rather than inferred**. `transform_<mob>`/`revert` route through `ServerGodAbilityExecutor.execute()` — the exact same single entry point every other ability goes through — which special-cases them with an early check before the god-type dispatch switch and hands off directly to `GodDisguiseHandler`. Not an alternate path instead of the executor; the executor's own first move for those two ability shapes. The class's own docstring states the wire format directly: `"transform_<mob>"` and `"revert"` cases exist "so Python AI can trigger transforms via the action frame channel." One precise new detail this settles: the real ability string is parameterized (`transform_<mob>`, target embedded via prefix), not a bare `"transform"` — explaining why it can't appear in [[action_format_sync]]'s fixed per-index table, and leaving one small, not-yet-chased-down thread: whether `god_controls.py`'s `ability_names()` (already confirmed to include `transform`/`revert`) actually assembles this parameterized string anywhere, not re-checked against this specific convention. `NetworkHandler.java` itself turned out to be narrower than its name suggested — one packet type only (`MorphSyncPacket`, visual sync to nearby players after a transform, not the dispatch point itself). `GodDisguiseHandler.java` contains a second, genuinely separate mechanism worth not conflating with the resolved question: a three-way form cycle (boss body/humanoid/disguise) on its own NBT key, unconnected to the transform/revert ability path. **Significant escalation, 2026-07-16, see [[GodEntityManager]]**: the server-side routing resolved here turned out to be reachable from nowhere — the client-side dispatch both [[WebSocketManager]] and [[TCPServer]] use is confirmed completely dead, by an exhaustive repo-wide search, not a guess.

[[GodEntityManager]], [[IGodEntity]] — **a significant escalation, not a new discovery from nothing**: chasing the "how does an AI-decided ability trigger actually reach [[ServerGodAbilityExecutor]]" thread flagged during the core wire-protocol batch led to the most consequential single finding of this whole Java-side ingest so far. `GodEntityManager.executeGodAbility()` — the confirmed dispatch target for both [[WebSocketManager]] and [[TCPServer]]'s incoming ability triggers — depends entirely on a `currentGodEntity` field. A repo-wide search for that field name turns up exactly six occurrences, every one inside this 81-line file: the declaration, four reads, one getter. **Never an assignment, anywhere in the codebase.** The AI-driven god-ability pipeline, through the live action-frame channel, cannot execute a single ability, for any god, currently — confirmed, not inferred. A second consequence, same root cause: `isGodEntity()`, which [[WebSocketManager]]'s own perception system uses to tag an agent's own body as `ENTITY_GOD`, is also always `false`. A plausible cause is documented in the class's own history: `FIX B-01` removed local client-side entity spawning (correctly — the old approach was illegal on a `ClientLevel` in Forge 1.20.1) in favor of the server spawning the real body and syncing it to clients — but nothing was added to _find_ that synced entity and populate `currentGodEntity` once it arrives. The follow-up half of a real fix appears to have never landed. Corrected/escalated on [[god-abilities]], [[ServerGodAbilityExecutor]], [[GodDisguiseHandler]], [[WebSocketManager]], and [[TCPServer]] — not left as a new, disconnected finding sitting only on this page.

[[WebSocketManager]], [[ActionExecutor]], [[TCPServer]], [[VisionCaptureSystem]], [[AudioCaptureSystem]] — **the core wire-protocol batch, closing [[communication-protocol]]'s biggest remaining gap.** `WebSocketManager.java`'s own class docstring documents nine named fixes (F1–F4, W1–W5) with real precision — an audio-metadata wire-format desync, `entity_count` hardcoded to `0` (perception could never see nearby entities at all until fixed), sound events silently never sent, and two resource-lifecycle bugs on reconnect. `collectNearbyEntities()` is a genuinely two-phase visual/audible system: raycasted line-of-sight for named entities, a wider unnamed "something's nearby" radius for anything occluded — sensing before seeing, deliberately modeled. **A real, precisely-scoped open thread surfaced, confirmed from _both_ the WebSocket and TCP receiving paths rather than assumed from one**: incoming god-ability triggers dispatch to `GodEntityManager.executeGodAbility()`, confirmed client-visual-only (it drives `IGodEntity.useAbility()` on an already-server-spawned body entity) — neither this nor [[ActionExecutor]] sends any custom network packet for an ability specifically, so the actual link from a client-decoded ability trigger to [[ServerGodAbilityExecutor]]'s server-side execution (already confirmed as the real entry point) isn't traced end-to-end yet. [[TCPServer]]'s own class docstring names a genuinely new lead for later: `actuators.py`'s `ForgeIPCClient.send_action()` as a _separate_ Python-side sender from `communication_protocol.py`'s WebSocket-based `BinaryProtocol` — not yet cross-checked, flagged for when `actuators.py` gets its own re-audit (already owed from the 2026-07-16 reconciliation). [[VisionCaptureSystem]]/[[AudioCaptureSystem]] are both clean, well-documented, single-purpose files — split pixel-readback-from-encoding for thread safety, dual-strategy OpenAL/javax.sound audio loopback capture — confirmed to feed exactly the fields [[WebSocketManager]]'s own perception-frame builder expects, no discrepancies found.

[[PythonBackendClient]], [[ProximityChatHandler]], [[AgentConfigLoader]] — **closes the Java-side "Python-dependent files first" priority batch entirely.** [[PythonBackendClient]] is a comprehensive confirmation file: every one of its nine methods maps onto a route already documented on [[main]], closing the loop on "is this route actually called from the Java side" for all of them at once — including confirming a real, live human-operator caller (`godUseAbility()`/`godTransform()`) exists for the two routes already confirmed as unimplemented stubs, which raises the stakes on those findings beyond a hypothetical future caller. [[ProximityChatHandler]] confirms, and importantly corrects, the NPC/god chat-routing split: every agent type (not just gods) gets the HTTP `notifyChatHeard()` call; NPCs additionally get chat via vanilla's `ClientChatReceivedEvent`, not via [[WebSocketManager]]'s own `sendChatObservation()` as that page had speculated — corrected there directly, with the real caller of `sendChatObservation()` now an open thread instead of a wrong guess. Also documents a real Forge event-ordering fix: the Oracle chat hook is called as a direct method invocation, specifically to sidestep Forge's cancelled-event listener semantics rather than depend on them. [[AgentConfigLoader]] closes the loop cleanly on all four confirmed call sites across [[OracleSystem]] and [[GodDisguiseHandler]], with one already-fixed historical bug (a JSON-array-vs-object parsing mismatch matching the exact "two independently-maintained parsers disagree about a shared format" pattern found repeatedly this whole session) and no live issues found. This closed the whole priority batch — the general Java sweep continued into the `entity/gods/` package below.

[[BaseGodEntity]], [[AIWither]], [[AIEnderDragon]], [[AIWarden]], [[AIElderGuardian]], [[AIOracle]], [[AICreaking]], [[GodSpawnHandler]], [[AICreakingEntity]] — **the full `entity/gods/` package plus the file that definitively answers what it all points to.** `BaseGodEntity extends Player` (not `Mob`) — full inventory/mining/crafting/trading/enchanting inherited essentially for free, a genuinely careful, "PRODUCTION READY"-labeled ~3,700-line implementation across all seven files. Every one of the six concrete gods independently confirmed the same client/server ability-parameter mismatch: `useAbility()`'s `"transform"` case expects a bare `"transform"` string plus a separate typed parameter, but [[ServerGodAbilityExecutor]]'s real wire convention is a combined `"transform_<mob>"` string with no separate parameter at all — and the parameter that *is* sent (three raw `float`s, confirmed on [[WebSocketManager]]/[[TCPServer]]) gets cast to whatever type each ability's own author assumed made sense (`String` for transform, `boolean` for Wither's `wither_skull`, `double` for Oracle's `teleport`) — three distinct `ClassCastException`-shaped bugs, not one repeated. `AIWither.java` also implements a sixth ability, `blue_skull`, absent from [[action_format_sync]]'s trainable action space entirely. `AIWarden.java` has its own hardcoded 5-second auto-emerge timer, directly contradicting [[ServerGodAbilityExecutor]]'s deliberately-timerless burrow/emerge design.

**All of it confirmed moot, definitively, by [[GodSpawnHandler]]** — read specifically to resolve where this was all heading. `spawnGodBody()` uses **vanilla Minecraft entity types** for five gods (`Warden`, `Wither`, `EnderDragon`, `ElderGuardian`, and `Evoker` for Oracle — the last one a deliberate, commented change away from a Wandering Trader specifically to avoid confusion with [[oracle-two-systems]]'s *other* Oracle system) and a separate, purpose-built `DivineWorld`-side class, [[AICreakingEntity]], for the sixth. It never constructs any of the seven `DWClientBot`-side classes. [[ServerGodAbilityExecutor]] operates on the entities [[GodSpawnHandler]] actually spawns, confirmed unambiguously for Creaking — [[AICreakingEntity]]'s own setter methods are explicitly commented "called by `ServerGodAbilityExecutor`." This resolves [[AIWarden]]'s burrow-timer discrepancy too: [[GodSpawnHandler]]'s own header comment confirms the live mechanic has no auto-emerge for either Warden or Creaking — `AIWarden.java`'s conflicting timer was never a competing live behavior, just dead code in a class nothing instantiates. One thread this leaves open: whether [[GodSpawnHandler]]`.replaceGodBody()` and [[GodDisguiseHandler]]`.applyTransform()` are the same transform mechanism under two names, or genuinely separate ones — not settled this pass. A new lead surfaced and not yet chased down: `GodControlHandler.java`, named directly in [[AICreakingEntity]]'s own comment as what syncs the invisible puppet player's position to the boss body every tick — the most promising remaining candidate for how a client-decoded ability trigger might actually reach the server, since [[GodEntityManager]] is confirmed not to be that path.
